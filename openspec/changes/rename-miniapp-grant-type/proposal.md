# Proposal: rename-miniapp-grant-type

## 背景

微信小程序登录作为尚未发布的新功能，当前实现将 OAuth 授权类型命名为 `xcx`。该缩写不够直观，现统一采用 `miniapp`。

## 问题陈述

SQL、后端认证策略、React/Vue 小程序客户端和说明文档使用 `xcx`，若只改动其中一处，客户端授权校验或 Spring 认证策略解析将失败。

## 目标与成功指标

- 成功指标 1：小程序客户端以 `grantType=miniapp` 登录时，后端可完成客户端授权校验并解析对应认证策略。
- 成功指标 2：增量 SQL 将冻结基线的小程序客户端 `client_key`、`client_secret`、`device_type` 和授权类型直接设为 `miniapp`，并同步小程序授权/设备字典；仓库业务引用不再保留 `xcx`。

## 变更内容

### 用户故事

- 作为：微信小程序用户
- 我希望：使用明确的 `miniapp` 授权类型登录
- 以便：前后端和客户端授权配置使用一致、可理解的协议值。

### 范围

统一小程序授权类型和客户端标识为 `miniapp`，覆盖 `sql/infoq_scaffold_update_20260713.sql`、后端认证常量/设备枚举、React/Vue 小程序登录与请求头、相关测试及说明文档。

### 非目标

不修改冻结初始化基线 `sql/infoq_scaffold_2.0.0.sql`；不改 Provider 编码、微信配置前缀、接口路径、OAuth 身份模型或登录流程；不实现 `xcx` 兼容与存量环境迁移。

### 约束

该功能尚未发布，因此直接切换协议值，不允许后端继续接受 `xcx`。SQL 仅为新功能脚本初始化 `miniapp` 客户端和字典数据；消息接收人索引使用直接 `ALTER TABLE ... ADD INDEX`，重复执行时报错由执行方处理。

## 验收约定

- 功能范围：统一小程序授权类型、`client_key`、`client_secret`、`device_type` 与请求头为 `miniapp`，并保证前后端策略、客户端授权配置和设备标识一致。
- 非目标：不修改冻结基线或稳定 `client_id`，不引入 `xcx`/`weapp` 客户端标识兼容，不改变微信 Provider、Taro/uni-app 运行时平台标识或现有登录副作用。
- 异常处理与阻塞：若定向测试、类型检查、构建或 UTF-8 校验失败，显式交付失败原因；不得通过兼容分支或放宽断言掩盖问题。
- 必需日志/验证证据：记录 OpenSpec 校验、精确检索、后端定向测试、React/Vue 小程序测试与构建/类型检查、UTF-8 校验和差异审查结果。
- 回滚触发条件：若部署后 `miniapp` 无法解析策略或客户端授权校验失败，恢复本变更的代码与脚本版本；因该功能未发布，不提供 `xcx` 数据迁移回滚脚本。
