# 测试数据策略

## 命名

所有自动化写入数据必须使用 `e2e_` 前缀。

CRUD runner 使用的名称格式：

```text
e2e_<client>_<stage>_<module>_<random>
```

`client` 区分 React/Vue，`stage` 区分新增/编辑；代码型唯一键可省略阶段。随机后缀保留完整 10 位十六进制（40-bit），长度约束只截断可读前缀，不能截掉随机量。最短用户名同样遵守此规则。

写入前对所选模块全部精确键做 DB preflight，冲突或查询失败立即停止，不删除既有键；本次 run 也不承担前次 fixture 的自动清理。随机后缀降低冲突概率，preflight 不是数据库唯一约束或并发锁的替代。

## 数据来源

- 优先通过 UI 创建真实数据。
- 需要 seed 时必须显式标记为测试 fixture。
- 不得修改 `sql/` 下的冻结初始化基线（唯一的 `infoq_scaffold_x.y.z.sql`）。
- 不得依赖生产默认口令或示例密钥作为新增测试数据。

## 数据隔离

- 不修改系统内置管理员、默认角色、默认菜单和默认配置。
- 不删除非 `e2e_` 数据。
- 涉及配置开关时必须先读取原值，失败时输出恢复命令或人工步骤。

## 高副作用数据

以下数据默认归为 P2：

- OSS 文件和 OSS 配置。
- 定时任务执行状态。
- 非当前 run 创建的在线用户会话。
- 缓存键。
- 账号锁定状态。
- 批量删除目标。

P2 场景执行前必须有显式门禁。在线强退只能使用当前 run 创建的 `e2e_` 用户会话 fixture，不得强退默认账号或共享在线用户。
