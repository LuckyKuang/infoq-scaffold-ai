# UI/UX 四阶段工作流

重大页面布局、导航结构或交互流程变更必须执行以下四阶段。已有布局内的小修复仍遵循验收约定和受影响工作区测试要求，不自动扩大成重新设计。若任务提供 MVP 约束文件，先读取并只覆盖核心用户流；偏离约束必须先提出议题并获得确认。

## 必需阶段与退出条件

| 阶段 | 交付物与执行要求 | 进入下一阶段的条件 |
| --- | --- | --- |
| Phase 1：布局方案 | 输出 Layout Specification 与 Desktop/Mobile ASCII Wireframe；说明页面区域、组件策略、关键交互、状态和 Responsive Strategy | 用户明确回复 `LAYOUT APPROVED` |
| Phase 2：静态演示 | 在 `docs/ui-demos/<change-id>.html` 生成独立静态演示，体现已批准的桌面/移动布局与关键状态，供用户实际查看 | 用户明确回复 `DEMO APPROVED` |
| Phase 3：正式实现 | 使用受影响工作区真实技术栈与组件库：React + Ant Design 或 Vue + Element Plus；按获批布局接入真实路由、权限和数据流 | 相关单元测试、必要 lint/build 通过，运行态可验证 |
| Phase 4：运行态验收 | 使用 `test-cli` 的 Playwright 或相应运行态工具核验真实 DOM、路由、桌面/移动布局与获批演示一致 | 证据完整且无未解决的必需验证失败；由主线程给出验收结论 |

审批必须针对本次具体产物；不得把讨论方案、生成 `design.md` 或用户未回复视为批准。若获批后核心布局或用户流发生变化，更新相应产物并重新取得该阶段批准。

### Phase 1 的最小内容

- 页面目标、参与角色、入口与主用户流，以及不在本次范围的功能。
- 区域层级、导航/筛选/主内容/辅助操作的位置与组件选型；查阅 `docs/DESIGN.md` 的组件 API 核验要求。
- 桌面与移动 ASCII 线框、断点策略、列表/表格适配、溢出和触控行为。
- 加载、空态、失败、无权限与成功反馈，以及键盘访问、焦点和可读性要求。

### Phase 2–4 的证据与边界

静态演示应独立打开并使用示例数据，不包含真实凭据或生产写操作，也不预设正式实现使用 Tailwind、Capacitor 或 Hono。正式代码遵循工作区现有路由、状态与组件结构，不能把静态演示直接当作业务实现完成。

运行态证据保存到 `tmp/`，至少记录实际访问路由、视口、关键操作、截图、console/network 异常与结论。受保护页面使用授权测试环境和验证码种子登录，不能为截图绕过鉴权。测试进程与 owned 端口按 `test-cli` 生命周期规则关闭；环境或外部服务缺失时明确记录阻塞，不宣称 Phase 4 已通过。

## 可选设计建议

以下内容仅辅助 Phase 1 选择视觉方向，不替代四阶段产物与审批。

## 目的

当视觉方向不明确、且你在实现前需要一份紧凑的设计建议包时，使用此覆盖层。

此覆盖层提供：

- 面向产品语境的风格方向建议
- 语义化颜色 token 建议
- 字体搭配建议
- 反模式约束
- 最小化交付前检查项

## 何时使用

仅在 Phase 1 且满足以下任一条件时使用：

- 用户提出“更高级 / 更现代 / 更精致”等抽象视觉目标
- 存在多个可行风格方向，需要显式选型
- 团队需要在静态 Demo 前先统一风格与 token 基线

以下场景可跳过本覆盖层：

- 目标工作区已有足够严格且可直接复用的设计 token 与样式规则
- 任务是无视觉方向变更的小型缺陷修复

## 输入契约

仅收集最小必要输入：

1. 产品类型（如 SaaS dashboard、fintech app、healthcare portal）
2. 页面类型（如 landing、admin 列表/详情、settings、checkout）
3. 用户感知关键词（如 trustworthy、playful、calm、dense、premium）
4. 平台上下文（React admin、Vue admin）
5. 约束条件（如 a11y 等级、性能敏感度、品牌要求）

## 输出契约

输出必须是紧凑建议包，并严格包含以下章节：

1. 风格方向：
   - 一个主风格
   - 一个备选风格
   - 各自一句简短理由
2. 语义色 token：
   - `primary`、`secondary`、`accent/cta`、`bg`、`surface`、`text`、`border`、`error`、`success`
   - 仅在 dark mode 在范围内时再给出明暗双套
3. 字体：
   - 标题字体与正文字体
   - 基础字号与层级步进
4. 交互规则：
   - hover/focus/disabled/loading 基线行为
5. 反模式：
   - 针对此上下文，列出 3-5 条明确“禁止项”
6. 验证钩子：
   - 与该页面绑定的 a11y 与响应式检查点

## 优先推理顺序

为保证输出稳定且节省 token，按以下顺序推理：

1. 可访问性与可读性
2. 交互清晰度与触达安全
3. 布局与响应式行为
4. 风格与品牌表达
5. 动效与精修细节

## 领域提示（精简）

- SaaS/B2B：优先信息清晰、层级明确、强调色克制、数据可读性高
- Fintech：优先可信感与稳健对比，避免过于炫目的渐变
- Healthcare：优先低噪声、可读性强、情绪平稳
- E-commerce：优先 CTA 显著性、可扫读性、商品卡一致性
- Content/Editorial：优先字距行距节奏、行长控制、留白节奏
- Creative/Portfolio：可允许更强风格表达，但导航预测性必须稳定

## 常见反模式

- 同一页面混用多套视觉语言且缺乏主次
- 在组件中散落使用原始颜色值，缺少语义 token
- 缺失焦点态与键盘可操作性
- 响应式仅在单一视口可用
- 装饰性动画遮蔽了状态变化

## 集成规则

此覆盖层不能替代协议门禁，必须继续执行：

- 静态 Demo 前获得 `LAYOUT APPROVED`
- 正式实现前获得 `DEMO APPROVED`
