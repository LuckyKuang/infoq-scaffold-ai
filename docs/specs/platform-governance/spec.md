# 平台治理规范

## 目标

定义仓库默认 AI 交付流程、统一影响矩阵、active change 结构校验、稳定规格回填纪律、仓库级 skill 与域外能力归属、OpenSpec 文档语言，以及文档审计覆盖、执行门禁和证据真实性要求。

## 要求

### 要求：分级 OpenSpec 流程
仓库变更必须按影响级别执行 OpenSpec 流程。

#### 场景：L3 高影响变更

- 当变更属于新功能、API 契约变更或跨工作区交付时
- 则实现开始前必须在 `openspec/changes/<change-id>/` 初始化变更
- 并且变更至少包含 `proposal.md` 与 `tasks.md`
- 并且实现前必须通过 `openspec-check`

#### 场景：L2 中影响单工作区变更

- 当变更只影响单工作区行为且不改 API 契约时
- 则允许采用 OpenSpec 精简流程
- 并且至少维护 `proposal.md` 与 `tasks.md`
- 并且交付前必须通过 `openspec-check`

#### 场景：L1 低影响小修复

- 当变更是单工作区小修复且不改契约、改动范围小（默认 `<=3` 个文件）时
- 则可以不创建 OpenSpec 变更目录
- 并且必须在任务上下文先写验收约定
- 并且若分级不确定，默认提升到 L3 执行

### 要求：统一影响矩阵
每个 change 都必须显式评估统一工作区或交付面，而不是只写当前编辑目录。

#### 场景：维护 `tasks.md`

- 当维护者编写或更新 `tasks.md` 时
- 则必须在影响矩阵章节内显式评估 `backend`、`frontend-react`、`frontend-vue`、`docs`、`script / deploy`、`skills`
- 并且对不受影响项必须给出原因

### 要求：active change 结构校验
active change 在实现前和交付前都必须通过统一结构校验。

#### 场景：校验 active change

- 当维护者准备进入实现或结束交付时
- 则必须执行 `node tools/openspec_check.mjs <change-id>`
- 并且缺少关键章节、影响矩阵或验证映射时必须显式失败

### 要求：稳定规格回填
稳定行为必须最终回写到 `docs/specs/`，避免长期依赖代码搜索。

#### 场景：活跃变更影响稳定行为

- 当某项变更明确改变或澄清了长期稳定行为时
- 则该变更必须在 active change 中补充 spec delta
- 并且在接受后回写到 `docs/specs/`

#### 场景：公共底座保存任务计划

- 当维护者记录具体任务的执行计划或活跃 change 时
- 则 `docs/plan/` 与 `openspec/changes/` 必须仅供本地使用，并由 Git 忽略，不得提交或进入 PR
- 并且后续执行计划继续写入 `docs/plan/`，目录不存在时按需创建，由用户手动清理
- 并且仓库级或高风险任务也不例外，版本控制只保留已接受的稳定规格、可复用操作流程与测试

#### 场景：开发者本地临时改后台端口

- 当开发者为避开本机 `8080` 冲突，临时把 admin backend 改到 `8081` 或其他端口时
- 则共享脚本、共享文档和真值配置仍必须保持 `8080` 作为默认值
- 并且 test-cli 本地栈 helper（`tools/lib/admin_dev_stack.mjs`）必须支持通过 `--backend-port <port>` 显式覆盖本地端口
- 并且前端 dev 代理必须自动跟随该显式端口，除非调用者显式设置 `VITE_APP_PROXY_TARGET`
- 并且该临时端口不得被沉淀为共享默认值

#### 场景：使用 `application-local.yml`

- 当维护者需要验证 `application-local.yml` 时
- 则必须显式传 `--spring.profiles.active=local` 或运行态脚本的 `--profile local`（`skills/test-cli/scripts/run_admin_e2e.mjs`、`run_admin_crud_e2e.mjs`）
- 并且排障时必须先区分 profile 未切换、端口错配、外部依赖不可达 三类问题

#### 场景：运行态脚本或 skill 启动长生命周期进程

- 当仓库级 skill 或 `tools/` 运行态脚本启动 backend、frontend dev server、浏览器 runner、WeChat DevTools runner 或其他长生命周期进程时
- 则必须在 `tmp/<owner>/`（skill 名或工具命令组名）或其子目录写入状态文件
- 并且状态文件必须至少记录 pid、端口、日志路径、启动时间、更新时间、拥有关系，以及 `starting`、`running`、`passed`、`failed`、`interrupted`、`stopped` 中的状态
- 并且验证完成、失败、阻塞中断或收到 `SIGINT`/`SIGTERM`/`SIGHUP` 时，必须关闭本次启动或状态文件标记为 owned 的端口
- 并且下一次运行前必须先清理仍标记为 `running` 或 `interrupted` 的旧状态，避免上次断开留下端口占用

### 要求：仓库级 skill 收敛与域外能力归属

仓库级 skill 必须保持 5 个 CLI 型工作域，域外验证与运维能力不得新增 skill。

#### 场景：新增或调整仓库级 skill

- 当需要新增 skill 或调整现有 skill 职责时
- 则只能归入 `compress-cli`、`push-cli`、`release-cli`、`test-cli`、`deploy-cli` 五个工作域
- 并且每个 skill 目录必须包含 `SKILL.md` 与 `agents/openai.yaml`，且 `default_prompt` 显式包含 `$<skill-name>`
- 并且标准执行顺序为判定范围 -> 只读探测/预览 -> 目标与影响枚举 -> 写入或危险动作门禁 -> 执行验证 -> `tmp/` 证据留存与显式失败

#### 场景：域外验证与运维能力

- 当出现无法归入上述 5 个域的能力时
- 则后端验证与 OpenSpec 校验放入 `tools/`
- 并且数据运维与交付工作流放入 `docs/`，部署脚本与运行时矩阵放入 `deploy/`
- 并且部署生命周期编排归 `deploy-cli`，不得为此新增 skill，也不得在 `skills/` 下保留 shared/README-only/helper-only 目录

#### 场景：AGENTS.md 压缩与路由校验

- 当创建、压缩或更新根 `AGENTS.md` 时
- 则必须执行 `node skills/compress-cli/scripts/agents_check.mjs check`
- 并且校验必须覆盖格式与唯一类别、受保护类别完整性、Local Skills ↔ `skills/` 目录 ↔ `docs/SKILLS.md` ↔ Skill Trigger 引用一致性，以及被引用路径是否存在
- 并且校验失败必须显式失败，禁止把失败当作环境噪声
- 并且脚本检查类别存在性与引用等结构约束；规则语义是否弱化必须另行人工审查，不能由结构通过推定

#### 场景：远程写操作

- 当任务涉及推送分支、创建或合并 PR、创建 tag 或发布 GitHub Release 时
- 则默认必须 dry-run，且只有显式 `--execute` 才执行远程写操作，合并仍须另传 `--yes`
- 并且预览不得创建本地分支、commit 或 tag；参数冲突与未知参数必须在写入前拒绝
- 并且禁止直推默认分支、禁止 `--force`/`--all`/`--tags`，禁止用 `--admin` 绕过分支保护

### 要求：SQL 初始化基线冻结
仓库初始化 SQL 必须保持冻结，数据库变更必须通过增量脚本交付。

#### 场景：数据库结构或数据变更

- 当变更涉及表结构、字典、菜单、配置、默认数据或其他数据库内容时
- 则不得修改 `sql/infoq_scaffold_3.0.0.sql`
- 并且必须通过新增当日 `sql/infoq_scaffold_update_YYYYMMDD.sql` 增量脚本交付，已应用的增量不得覆写
- 并且交付说明必须写清脚本执行、缓存清理或重启要求，以及回滚影响

#### 场景：发现初始化 SQL 被误改

- 当差异审查发现 `sql/infoq_scaffold_3.0.0.sql` 出现变更时
- 则必须先回退该初始化 SQL
- 并且把必要变更迁移到当前日期增量脚本
- 并且重新执行相关规约和编码校验

### 要求：MVC JSON 大数保护

Spring MVC JSON 输出必须对超出 JavaScript 安全整数范围的整数做字符串化保护。

#### 场景：雪花主键返回给浏览器

- 当任一接口返回 `Long`、`long` 或 `BigInteger` 字段且绝对值大于 9007199254740991
- 则 JSON 输出中该字段必须为字符串
- 并且浏览器端解析后必须能以精确原值回传给编辑、删除等接口

#### 场景：安全范围内整数保持数字

- 当接口返回 `long` 或 `Long` 字段且绝对值不大于 9007199254740991
- 则 JSON 输出中该字段必须保持数字类型


### 要求：归档前验证
受影响工作区的验证证据完整前，变更不得归档。

#### 场景：验证完成

- 当 `openspec-check`、主流程验证、目标测试、必要 lint/build 已通过，或存在获批例外时
- 则该变更可被认定为满足归档前提

#### 场景：验证受阻

- 当任一必需验证步骤阻塞或失败时
- 则该变更必须保持活跃状态
- 并且阻塞信息必须在当前变更文档产物中显式记录

### 要求：OpenSpec 文档语言规范
`openspec/` 下新增或更新文档正文必须默认使用中文。

#### 场景：编写 OpenSpec 文档

- 当维护者编写 `openspec/` 下文档时
- 则正文与说明应使用中文表达
- 并且路径名称、命令、文件名保持英文原样

#### 场景：工具兼容

- 当需要与自动化流程或脚本兼容时
- 则文件名继续使用 `proposal.md`、`tasks.md`、`design.md`、`materials.md`、`review.md`、`spec.md`
- 并且不得为语言本地化而改动这些标准文件名

### 要求： 文档审计覆盖可追溯

仓库级全面文档审计 必须 为当前仓库维护的 Markdown、全部层级规约、技能及脚本/配置说明入口建立覆盖清单，MUST 为每项记录检查状态、核查依据与结论，并为排除项记录原因；脚本入口、CLI 帮助、技能 metadata、配置示例、package scripts 与 CI 工作流 必须 独立盘点，不得仅依赖 Markdown 引用发现。

#### 场景： 全仓文档盘点

- 当 维护者执行全仓文档准确性审计
- 则 清单覆盖根目录、工作区、隐藏维护目录、`docs/`、`deploy/`、`skills/`、`tools/` 与 `openspec/` 中的仓库维护文档
- 并且 第三方依赖、缓存和生成产物的排除范围可见，未检查项目不能被统计为通过

#### 场景： 审计期间新增维护文件

- 当 审计修订新增了文档、脚本或其他纳入范围的维护入口
- 则 交付前重新盘点，将新增项目纳入覆盖清单并完成对应核查
- 并且 仅标记“已读取”而缺少事实核对依据的项目不能认定为审计完成

#### 场景：再次执行全面复核

- 当仓库已有历史审计报告或临时覆盖清单而维护者再次执行全面复核
- 则必须从当前维护文件独立生成文档与操作入口清单，并为本轮每项记录事实来源与结论
- 并且必须重新确认历史问题的当前状态，不得直接复用旧数量、通过结果或阻塞冒充本轮核查
- 并且交付前再次盘点新增项目，最终不得存在漏项、重复认领或未核查项

### 要求： 文档声明与实现一致

文档 必须 以受管配置、脚本和工作区实现为事实依据；命令、参数、路径、版本、环境前置条件、默认值、产物位置及操作边界 必须 与对应实现一致，涉及官方产品行为的说明 必须 有适用的官方依据。

已接受的稳定要求与实现不一致时，必须区分实现缺陷和文档漂移，不得降低要求制造一致性；进程生命周期、退出状态和清理边界同样属于文档契约。

#### 场景： 修正文档漂移

- 当 文档声明的 CLI 参数、默认配置或文件路径与当前实现冲突
- 则 维护者记录文档位置与对应实现证据，并修正声明或直接服务本次目标的错误校验行为
- 并且 相关入口、规约、技能及引用文档同步更新，不保留互相矛盾的当前说明

#### 场景： 无法核实声明

- 当 声明依赖当前不可访问的平台、服务或生产状态
- 则 记录具体缺失条件及其影响，保留未验证状态，不猜测运行结果
- 并且写明关闭标准；范围内已确认的文档错误仍须修正

#### 场景：配套脚本违背已接受要求

- 当脚本缺陷影响文档承诺且可在授权范围内隔离复现与验证
- 则必须完成根因导向的最小修复，并用正常和失败场景证明行为及副作用边界
- 并且不得通过删除稳定要求、放宽断言、吞错或把查询失败解释为空结果宣称问题解决

### 要求： 远程写 CLI 默认安全预览

push/release CLI 的远程写命令 必须 默认预览且不产生远程写入，预览 必须 不创建本地分支、commit 或 tag，实际执行 必须 显式传入 `--execute`；现有合并确认、目标校验、鉴权及分支保护 必须 保留，帮助、技能、规约和当前文档示例 必须 同步说明实际行为。该要求不改变本地版本同步命令 `bump` 的职责，其 `--dry-run` 必须 保持不写入受管版本文件。

#### 场景： 未显式请求执行

- 当 维护者未传入 `--execute` 调用 `push`、`submit-pr`、`merge`、`tag` 或 `publish`
- 则 命令仅展示计划或明确报告缺失前置条件，不执行远程写入，也不创建本地分支、commit 或 tag
- 并且 隔离回归验证默认路径没有发出这些写命令，不连接真实远程验证此约束

#### 场景： 显式执行与参数校验

- 当 维护者显式传入 `--execute` 请求远程写入
- 则 CLI 仅在满足该命令原有前置校验与确认条件后进入执行路径
- 并且 未知参数或互相冲突的执行参数明确失败，不能通过参数顺序覆盖危险操作门禁

### 要求： 部署文档具备完整操作条件

当前部署与发布文档 必须 明确适用平台、环境/配置/依赖前置条件、执行门禁、健康验证、失败诊断和回滚条件；涉及凭据的说明 必须 保持安全边界，不得通过文档泄露实际敏感值。

#### 场景： 维护者按照部署文档准备执行

- 当 维护者选择一个文档声明支持的部署运行时
- 则 能找到与实际脚本一致的预检、目标枚举、执行授权、健康检查、日志和回滚说明
- 并且 涉及共享环境、数据、部署状态或远程写入的操作保持相应确认门禁

#### 场景： 生产凭据准备未完成

- 当 部署仍使用仓库示例密码、示例 RSA 配置，或无法确认生产凭据来源及配置匹配情况
- 则 规约与部署文档 必须 将其列为生产准备阻塞，并说明独立受控凭据及当前协议配置要求
- 并且 文档只允许在明确隔离的开发/演示场景使用示例值，不把文档修正当作凭据已经替换或生产已经验收
- 并且 文档审计不实际轮换或输出凭据

### 要求： 审计证据与完成状态真实

审计 必须 把临时清单和校验输出保存在 `tmp/`，把耐久结论与治理规则保存在仓库文档；MUST 按真实结果区分已修复、已验证、失败、阻塞及未验证项目，不得把静态检查等同于生产运行验收。

#### 场景： 交付全面文档审计结果

- 当 维护者提交本次文档审计结论
- 则 结论列出覆盖范围、主要修正、校验命令与结果，以及缺失平台或运行条件
- 并且 性能影响、可观测性、回滚路径、配置/SQL/依赖影响均有检查结论或明确残余风险
- 并且区分本轮和历史证据，静态检查、隔离回归及历史运行结果均不能替代本轮生产验收

#### 场景： 文档或治理工具修复引入回归

- 当 修复造成事实失真、权限门禁弱化或验证回归
- 则 立即撤销本次错误修改并重新定位原因
- 并且 不覆盖用户或协作者的修改，不通过削弱测试或校验器制造成功结果

### 要求：生产保障结果以本轮环境证据为准

交付必须分开列出仓库修复、单元/隔离回归、目标平台运行与实际生产验收；必须 不用 fixture、静态配置、未执行的 CI 矩阵或旧轮次通过记录替代本轮实际运行。

#### 场景：平台矩阵和缺失条件

- 当修改跨平台 CLI 或部署流程。
- 则CI 与可复用 SOP必须覆盖所声明的平台及支持边界，每个实际执行的结果必须包含版本、命令、退出/清理状态。
- 并且不可用的 Windows/WSL/Linux/Apple、远端 Actions、生产秘密或真实 Provider必须标为具体 blocked/未验证，必须 不阻止可独立完成的仓库修复。

### 要求：告警与容量验收可复用且不伪造达标

运维能力必须提供有明确输入、限时、目标范围与输出的容量测量及告警触发/恢复步骤；必须 区分监测信号、告警规则和实际外部接收证据，不把 healthcheck 当作完整告警。

#### 场景：缺少生产验收目标

- 当未提供容量 SLO、RTO/RPO 或告警接收人。
- 则工具/SOP必须输出可测量结果和缺失条件，必须 不臆造目标或声称达标。
- 并且高负载、故障注入和恢复操作必须仅作用于显式选定且已授权的隔离 owned 目标。

#### 场景：运行保障交付
